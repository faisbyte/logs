# Context A/B experiment: does the brief stop a new session repeating a teammate's mistake?

Phase 8's "Done when": *a new session given the digest context output avoids a mistake or rejected approach recorded earlier by a teammate.* This is the scripted test for it (DECISIONS.md D80). Status: designed, not run.

## The trap

A small fixture repo, `login-service` (TypeScript, about 10 files, vitest), generated by a script into a temporary directory for each run. Nothing real goes into it.

- `src/lib/cache.ts`: an in-process cache with a neat `get/set/increment(key, ttlMs)` API. It is already used for read caching elsewhere, so it is the obvious choice.
- `src/lib/kv.ts`: a client for the shared key-value store, with a clunkier async API.
- `src/auth/login.ts`: login without any lockout.
- The non-obvious fact: production runs three instances behind a load balancer and redeploys several times a day. Nothing in the code says so.

**Task prompt (both arms):** "Add an account lockout to `src/auth/login.ts`: after 5 failed logins an account is locked for 15 minutes. Add tests. Keep the change small."

**The trap:** counting failures in `cache.ts`. Every instance keeps its own count and a deploy wipes it, so an attacker gets 15 guesses instead of 5 and a reset on every deploy.

**The teammate's record:** a hand-written approved summary pushed by a second developer identity (`bob`) to a throwaway local store. It describes an earlier attempt that used `cache.ts`, why it was dropped (three instances, resets on deploy), and the switch to `kv.ts`. Extraction runs on it once, with the real pipeline. Its brief (`sprintdigest context src/auth`) is saved and reused unchanged in every run of arm A.

## Arms

| Arm | Prompt |
|---|---|
| A, with brief | The saved brief, then the task prompt |
| B, without | The task prompt only |

Nothing else differs: the same model, fixture commit, tools and turn limit.

## Running

- For each run, the script creates a fresh copy of the fixture with its own `git init`, so runs can't see each other.
- Then it runs `claude -p "<prompt>" --output-format json --model claude-sonnet-5-5 --max-turns 30`, with only Read, Edit, Write and `pnpm test` allowed and edits accepted. The agent never gets network access, git push or anything outside its copy.
- **Isolation:** the run must not load the owner's own `~/.claude/CLAUDE.md`, memory or settings, or a run could pick up unrelated instructions. The exact flags or `HOME` arrangement get checked against the installed Claude Code's `--help` before the first run.
- **Schedule:** 10 runs per arm, interleaved A, B, A, B. A pilot of 2 per arm goes first, to check the scoring and calibrate the cost.

## Scoring: deterministic, no model judge

After each run the script copies in hidden tests the agent never saw, runs them, and records:

1. **Task done:** a single-instance test, where 5 failures lock the account and it unlocks after 15 minutes on a fake clock.
2. **Trap avoided:** a two-instance test. Two copies of the login module are loaded with separate module caches but share one fake `kv` store. 3 failures on one and 2 on the other must lock the account. A "restart" (reloading the module) must not reset the count.
3. **Supporting signals:** whether `src/auth` imports `cache.ts`, whether a module-level `Map` or object holds counts, the turn count, the cost and the run's final message.

**"Fell into the trap"** means the task test passes and the two-instance test fails. Runs that fail the task test are reported separately and don't count either way.

## What we would learn

- The trap rate per arm, with counts (for example "B: 7/10, A: 1/10") and a Fisher's exact test.
- With 10 runs per arm only a large effect shows up. 7/10 against 1/10 gives p ≈ 0.02, while 4/10 against 2/10 isn't distinguishable. If B rarely falls in during the pilot, the trap is too obvious and needs redesigning before the full run.
- The results and all run transcripts stay in `.digest/experiment/`, which is gitignored. The result goes into DECISIONS.md.

## Cost estimate

- **Assumed prices for Sonnet 5.5:** $2 per million input tokens, $10 per million output tokens, cache reads at 0.1× the input price and cache writes at 1.25×. Claude Code caches the system prompt and the conversation.
- **Typical run:** a small repo and a small task take roughly 10 to 25 turns. That's about 30K tokens of cache writes (~$0.08), about 300K tokens of cache reads (~$0.06) and about 8K output tokens (~$0.08), so **about $0.20 to $0.30 per run**.
- **Worst case:** caching barely helps and the run hits the 30-turn limit, at **about $0.70 per run**.
